# Doc 10 — Days 46–60: Phase 4, AIOS Integration (Revised)
### From code visualizer to multi-tool agent — MCP, RAG, checkpointing, and full agent breadth

---

## Why this revision exists

The first draft of this doc covered tools and orchestration but missed several things v1.2 (the original 34-day AIOS curriculum) treated as core: MCP servers, real RAG, resumable state, and safety-by-architecture rather than safety-as-an-afterthought. This version folds all of it in — same 15 days, no extension, some lower-priority items cut instead (see the master syllabus doc for the full list of what's cut and why).

Same ground rules as Docs 00–09: ~3 focused hours/day, "done when" gate per day, slide the calendar if you fall behind rather than skipping a block.

---

## Block A — Days 46–50: Tools, MCP, Browser

**Day 46 — Tool abstraction, MCP-shaped**
Define a `Tool` interface: name, description, JSON schema, `execute()`. Refactor the Phase 3 code-evaluator into the first registered tool. Decide **read-tools vs act-tools** right here, as an architecture rule, not a Day 57 afterthought — every tool gets tagged one or the other, and act-tools get gated by default from this point forward.
*Done when:* the code-evaluator runs through the registry, tagged `read`, and existing Phase 3 tests still pass unmodified.

**Day 47 — Your own MCP server + consuming an external one**
Wrap your tool registry as a real MCP server (Python `mcp` SDK) so Claude Code or Claude Desktop can call your tools directly. Separately, connect to one external MCP server (filesystem or GitHub) and call it from your agent.
*Common mistakes to avoid:* servers with god-level permissions, tools with undocumented side effects, assuming every MCP server you find online is safe to install — it's arbitrary code.
*Done when:* you can call your own AIOS tool from Claude Desktop, and your agent can call a tool from an external MCP server.

**Day 48 — Planner/router, with guards from day one**
Given a task, the agent picks a registered tool (structured-output routing). Bake in loop guards (max iterations, max tool calls) and a spend cap now — not later. Extend your tracer's step schema to log `tool_call → result → retry`.
*Done when:* a task with no matching tool fails safely (guard trips) instead of looping.

**Day 49 — Browser tool, part 1**
Wrap Playwright as a registered tool, reusing Phase 2. Favor high-level task tools (`search_flights(origin, dest)`) over low-level click primitives — more reliable, easier to gate. Low-level browsing is powerful but failure-prone; that tradeoff is a deliberate choice, not a shortcut.
*Done when:* the planner routes a "find X on this page" task to the browser tool correctly.

**Day 50 — Browser tool, part 2 + integration checkpoint**
Multi-step browser tasks with session persistence for logged-in sites. Mini project: a "morning scout" — agent visits 2–3 sites you actually check daily and produces one digest.
*Done when:* the digest runs end to end without you babysitting each step.

## Block B — Days 51–55: Email, Docs, RAG, Checkpointing

**Day 51 — Email + Calendar tools**
Real OAuth 2.0 flow for Gmail/Calendar (walk the full flow, don't shortcut it). Read/search inbox and calendar as read-tools. Draft (never auto-send) as an act-tool.
*Done when:* the agent can draft a reply and it sits unsent, waiting.

**Day 52 — The approval gate, built once, generically**
One approval mechanism that every act-tool routes through — not a per-tool hack. Document tool (Drive API read/write) reuses Day 51's OAuth pattern, so this should move faster than email did.
*Done when:* every act-tool you've built so far (email send, doc write) requires the same approval step to fire.

**Day 53 — RAG foundations, plain Python**
Embeddings (one API call), a plain-Python vector store — a list/dict or SQLite table with cosine similarity, no LangChain or heavy framework. You're learning what RAG actually does, not a framework's abstraction over it.
*Done when:* you can embed 10 documents and retrieve the 3 most relevant for a query, by hand, and explain why each one ranked where it did.

**Day 54 — Research tool, for real this time**
Web search + retrieval into the Day 53 store, synthesized into structured JSON (reuses Phase 3's structured-output work). This is now genuinely RAG, not search-and-read.
*Done when:* all 6 tools — code, MCP, browser, email/calendar, docs, research — are independently registered and callable.

**Day 55 — Checkpointing: the kill test**
Persist orchestrator state (task, current step, partial results) to a file or SQLite row. Kill the process mid-run. Restart it.
*Done when:* it resumes exactly where it died, not from scratch.

## Block C — Days 56–60: Orchestration, Safety, Capstone

**Day 56 — Business automation = orchestration, not a new tool**
Chain tools into a multi-step workflow on top of Day 55's checkpointing — e.g. research a topic → draft a summary doc → draft a follow-up email referencing it.
*Done when:* one instruction produces a correct 3-step plan across 3 tools, and surviving a kill mid-workflow doesn't restart it from step 1.

**Day 57 — Safety audit**
Prompt-injection test against the *full* tool set together, not one tool in isolation — feed it a page or email with embedded instructions and confirm it doesn't obey them. Answer, in writing: what's this agent's blast radius if fully compromised today?
*Done when:* the injected instruction is not obeyed, and you can answer the blast-radius question in under a minute without hedging.

**Days 58–59 — Capstone, build + debug**
Full scenario spanning every tool: research a lead → draft a personalized email → save a summary doc → wait for approval → send. Day 59 is deliberately debugging time — multi-agent systems break between tools, not inside them.
*Done when:* the scenario runs unattended except for the one approval step.

**Day 60 — Demo & wrap**
Visualize the full multi-agent trace live in your tracer UI. Record it.
*Done when:* you can watch, step by step, exactly which tool ran, what it changed, and where it retried.
